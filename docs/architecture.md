# Architecture

## Overview

TimeLineEditor (TiLiE) is a browser editor and visualization tool for musical timelines represented by `timetoalign`. It works with three layers, each named by one word only:

- a **manifest** is one timeline as the `timeskeleton` schema (version 0.4.0) describes it: `{meta, timeline, graphical?}`, the timeline with exact rational coordinates, children at exact offsets, conversion maps, regions, flow control, measure maps and metric hierarchies, and the style rules of its own drawing. A manifest knows nothing about where, or how often, it is shown;
- a **block** is a record that carries one manifest together with its placement on the canvas: position, scale, zoom, margins, background, name column and block-level style overrides;
- a **workspace** is the canvas: a set of records (blocks and, later, other kinds), their order, the workspace settings, and the namespace of record ids that addresses everything in it.

TiLiE is local-first from the start: the browser communicates with a local Python server. The server is not an incidental wrapper. It owns loading through `timetoalign`, heavy computation, and exports, while the browser keeps a small editing core. This division keeps Python library capabilities close to the operations that need them and keeps interaction responsive without a per-keystroke network request.

## What exists today and what is planned

The executable product today is intentionally small. `tilie-server` starts a FastAPI server on loopback, serves the built browser shell, and answers authenticated `GET /api/health`. The Svelte shell has three empty fixed panes, Arranger, Inspector, and Diagnostics, plus a health readout.

Of the six workspace packages, `core` implements the three layers in memory: exact numbers, validated manifest load and save, the immutable workspace view with its records, ids and order, the command vocabulary over both, and a Yjs binding of one manifest ([The core package](#the-core-package)). `layout` and `writers` implement the drawing of a manifest as one block: its geometry in exact numbers, and SVG and TikZ text written from that geometry ([Layout and writers](#layout-and-writers)). The other three establish exports, strict type checks, dependency boundaries, and tests, rather than editing behavior, and the editor shell uses none of these packages yet.

A file format for a whole workspace, a Yjs binding of the workspace, on-screen rendering and interaction, loading through the server, raster exports, generated API clients, collaboration over a network, and automation endpoints are not implemented. Except for the core, layout and writers packages, the remaining sections describe the intended architecture so additions have explicit boundaries; they do not describe current behavior as available functionality.

## The canvas

The canvas is a data-driven renderer rather than a diagram engine. It has two levels. At the workspace level, blocks are placed freely or locked to each other at coordinates, beside the other kinds of record; interaction includes drag, snap, selection, pan, and zoom. A block draws one manifest, which today describes one timeline with its children; later versions of the schema may let a manifest describe a group of timelines or an alignment bundle instead.

At the block level, geometry comes from the manifest rather than from an editable drawing surface. Time maps to x through the block's placement (today a linear map of scale 1 in abstract units, which the writers turn into page units; the block record already stores the `scale` and `zoom` an on-screen renderer will use, and elision segments are an intended addition). A layout over children, conversion maps, regions, and flow arcs determines the rows and the other shapes. A person edits the underlying manifest through commands, never by dragging an arrow endpoint. This preserves the meaning of a musical relation independently of a particular display.

## Exact values and commands

Exact rationals travel end to end. A coordinate is one atomic value, `{ unit, number_type, value }`, never a container of separately editable parts; its value is a JSON integer, a JSON number or a `[numerator, denominator]` Fraction pair as the number type selects, following the BOPP core primitives. Geometry stays exact as well: every horizontal position is a value on the root timeline's axis in the manifest's own number forms, and every vertical position an integer row or an exact fraction of one. Only the writers turn positions into page coordinates, and they round only when they write a number. Canvas quantities of a record (position, scale, zoom, margins) are plain finite numbers: they place a drawing and carry no musical meaning.

Every user operation is a named, serializable, validated command. Commands are the single entry point for the UI, tests, and automation. Before applying an edit, command handling checks invariants such as containment, number type, and unit. The schema validates a manifest on load, on save, and whenever a command brings one into a block.

A CRDT store is the persistence and synchronization base: Yjs in the browser (implemented in `core` for one manifest) and pycrdt on the server (intended), with history and offline autosave to follow. Event tables remain outside the manifest and move as Arrow data rather than being embedded in TimeSkeleton.

## The core package

`@timetoalign/tilie-core` is framework-free: no DOM, no Svelte, no network. It has two entry points. The root export holds the numbers, the manifest types, `loadManifest`, `saveManifest` and `checkManifest`, the workspace view and records, ids and order keys, `parseCommand`, `applyToManifest` and `apply`, and the error types; it never imports Yjs. The subpath `@timetoalign/tilie-core/yjs` holds the Yjs binding of one manifest: `manifestMap`, `readManifest` and `syncManifest`. Yjs is an optional peer dependency, so a host that needs only the reducers installs no CRDT. Two dependency-cruiser rules keep it so: only `src/yjs/` (and the tests of `core`) may import `yjs`, and nothing else in `core` may import `src/yjs/`. The package needs Node 22.18 or later, as `@timetoalign/timeskeleton` does.

### Numbers

`Rational` is an exact fraction over `BigInt`, always normalized (positive denominator, lowest terms), with exact addition, subtraction, multiplication, division and `floor`. It is built from a `[numerator, denominator]` pair, a `bigint`, a safe integer or a decimal integer string, and never from a JavaScript float: `0.5` and `2 ** 53` are refused. A `Real` is a value as Python's numeric tower holds it, an exact `Rational` or a float; `addReal` and `compareReal` combine and compare such values as the tower does (a sum involving a float is a float, a comparison is exact), and `realOf` reads a coordinate's value as one. `fromFloat` returns the exact binary value of a float, as Python's `Fraction(float)` does, and `toFloat` the double nearest to a `Rational`; `fromFloat` serves arithmetic that must be exact on a float's value, such as the writers' page transform, and never re-expresses a coordinate. A `Coordinate` is `{unit, numberType, value}` whose value is what the axis's number type declares: a `bigint` for `int`, a `number` for `float`, a `Rational` for `fraction`. `coordinateFromDict` and `coordinateToDict` mirror timetoalign's `coordinate_from_dict` and `coordinate_to_dict`: an `int` axis reads a JSON integer, or an integral JSON number as that integer; a `float` axis reads a JSON number, or an integer as the float it equals exactly; a `fraction` axis reads only a pair; every integer is int64-bounded. Arithmetic and comparison (`addCoordinates`, `subtractCoordinates`, `compareCoordinates`, `coordinatesEqual`) work within one axis only, and throw `AxisMismatchError` across units or number types.

### The manifest value

A loaded manifest is exactly the value `@timetoalign/timeskeleton`'s `parse` returns for a valid 0.4.0 manifest, typed member by member (`Manifest`, `TimelineManifest`), including the optional `graphical` block of style rules. Every number in it is a `JsonNumber`: a plain `number` for a safe integer or a float with a fractional part, a `bigint` for an integer beyond 2^53, and a `JsonFloat` for an integral float, so that `600.0` stays a float and is written back as `600.0`. A command that carries a float whose value is an integer passes it as a `JsonFloat`. `core` reads, orders and writes no JSON of its own: reading, migration, the canonical order and the standard writer are the schema package's.

### Load and save

`loadManifest(text)` reads the text with `parse` (which validates it against the schema version it declares), migrates a published envelope (the multi-timeline shape of schema versions 0.1.0 to 0.3.0) to a manifest, validates the result, and then checks every invariant. It returns the manifest in canonical order, or a `LoadError` whose `problems` list `invalid_json` for text that is not JSON, the first `schema_violation` or `migration_failed` with the path the shared validator reports, or every invariant violation of a schema-valid manifest. An envelope that holds more than one top-level timeline is refused as `migration_failed` at `manifest.timelines`; the schema package's `split` divides it into envelopes that load one by one. `saveManifest(manifest)` validates the manifest and checks its invariants, throwing `InvalidManifestError` with every problem, and writes it with the schema package's `dumps`: canonical order, the standard text, byte-identical to what the Python writer produces. Every 0.4.0 manifest fixture of the schema package loads and saves to its own bytes.

### Commands

Every edit is a command, a plain JSON object `{type, ...}`, and `apply(view, command)` applies any of the 24 to a workspace view (`COMMAND_TYPES` lists them; `MANIFEST_COMMAND_TYPES` and `RECORD_COMMAND_TYPES` the two kinds). `apply` is a pure reducer: it never modifies its input and returns either the new view or a `CommandError` `{code, message, path}`.

The sixteen **manifest commands** edit the manifest of one block, named by the command's `block` member: `setName`, `setLength`, `addChild`, `setChildOffset`, `removeChild`, `addRegion`, `setRegion`, `removeRegion`, `addBreak`, `removeBreak`, `addJump`, `removeJump`, `setMarker`, `removeMarker`, `addConversionMap` and `removeConversionMap`. Within the manifest, a timeline is addressed by its id, which is unique across the manifest; a region or a marker by its name; a conversion map by its id; a break or a jump by its full value. Nothing is addressed by an array index. `addChild` creates a new timeline in a parent at an offset and locks it; `removeChild` deletes the subtree. The top-level timeline is never removed by a manifest command; the block that carries it is. Class, unit and number type are fixed when a timeline is created. Conversion-map payloads, `meta`, `measure_map` and `metric_hierarchy` are carried verbatim, never edited member by member. `applyToManifest(manifest, command)` is the same reducer for one manifest outside a workspace; the command still names its `block`.

The eight **record commands** edit the workspace: `createBlock` (a new block with a given id, carrying a manifest, at a position; its other properties come from the workspace's block defaults), `moveRecords` (several positions at once), `resizeRecord` (a block's scale), `setRecordProperties` (a block's zoom, margins, background, name column or style overrides), `setIndex` (a record's order key among its siblings), `deleteRecords` (records with all their descendants), `setSettings` (the workspace settings, member by member) and `setBlockManifest` (replace a block's manifest). A manifest that a command brings into a block goes through the same path as `loadManifest`, so an envelope with one top-level timeline is migrated and an invalid manifest is refused.

`parseCommand(value)` reads a command from any value, as a user interface or an agent sends it, refuses unknown or extra members, malformed record ids and non-finite canvas numbers, and normalizes coordinates as the library does (`[2, 4]` is stored as `[1, 2]`); a coordinate on another unit or number type is refused, never converted. A refusal by `apply` points into the view the command was applied to: `["records", <id>, …]` for a record command, and `["records", <block id>, "manifest", …]` for a manifest command, followed by the member of the command at fault (a refused value is not in the view). `applyToManifest`, which has no view, reports that member alone, and a command that `parseCommand` rejects as malformed reports the path of the malformed member in the rejected value. The codes are stable strings, exported as `ErrorCode`:

- reading: `invalid_command`, `invalid_coordinate`, `schema_violation`;
- the workspace: `unknown_record`, `duplicate_record`, `invalid_record_id`, `not_a_block`, `unknown_parent`, `parent_cycle`, `invalid_index`, `duplicate_index`, `invalid_address`, `non_finite_number`, `non_positive_number`;
- addressing within a manifest: `unknown_timeline`, `unknown_region`, `unknown_break`, `unknown_jump`, `unknown_marker`, `unknown_map`, `not_a_child`;
- manifest invariants: `unit_not_allowed`, `number_type_not_allowed`, `off_axis`, `child_unit_mismatch`, `negative_offset`, `child_exceeds_parent`, `locked`, `length_below_content`, `negative_length`, `duplicate_region`, `region_end_before_start`, `duplicate_map`, `map_source_unit_mismatch`, `duplicate_timeline`;
- loading and checking only: `invalid_json`, `migration_failed`, `child_not_locked`, `key_mismatch`, `metric_hierarchy_without_measure_map`.

### Invariants

The manifest invariants are timetoalign's, checked twice: by `checkManifest` over a loaded manifest and by each reducer before its edit applies. A class admits its units and a unit its number types; a child has its parent's unit and a non-negative offset, ends within its parent, and is locked when placed; a locked timeline's length cannot be set, and no length falls below the end of a child; region names and conversion-map ids are unique on a timeline; a region does not end before it starts; a map's source unit is the timeline's unit; a metric hierarchy needs a measure map. A child placed past the end of an unlocked parent lengthens the parent to the child's end; a locked parent refuses. The catalogue in `app/packages/core/tests/README.md` lists every row.

Five rules go beyond what the library enforces, because the editor addresses and stores values directly and refuses a manifest the library would not have written: timeline ids are unique across the whole manifest, a child stored under a key has that key as its id, a loaded child is locked (the library writes every child with `locked: true` and would silently lock one that is not), a coordinate of a region or of flow control must already carry the axis's number type (the library would re-express it), and a parent grows only to a value its own number type holds exactly (an `int` parent cannot grow to 9/2, a `float` parent cannot grow to 1/3). What the library does not enforce, `core` does not invent: a region, break, jump or marker may lie outside its timeline, and any number of breaks or jumps may share a coordinate.

A child shares its parent's unit but may have another number type. Its end, offset plus length, and every comparison against it follow Python's numeric tower: an `int` and a Fraction are exact, a sum with a float is a float with each exact operand correctly rounded first, and a float compares with an exact value exactly.

### The workspace view

A workspace is held as a `View`, an immutable plain value: `meta` (`format: "tilie-workspace"`, `version: 1`, the creation date and the generator), `settings` and `records`, a map from record id to record. `createView(meta, settings)` returns an empty view, with `DEFAULT_SETTINGS` unless other settings are given: no workspace style rules, the block defaults (scale 40, zoom 1, margins of 16 on every side, no background, a visible name column a quarter of the plot wide) and an 8-unit grid with snapping.

Every record has an `id`, a `kind`, a `parent` record or `null`, and an `index`, its order key among the records of the same parent. The kinds are `block`, `text`, `connector`, `lock`, `group`, `shape` and `image`; only blocks have commands so far, and the other record types are stable extension points. A `BlockRecord` holds the canvas properties listed in [Overview](#overview) and its `manifest`. `checkWorkspace(view)` returns every problem of a view, by record id: a record stored under another key, a malformed id, a missing parent, a cycle of parents, a malformed order key or one shared with a sibling, a canvas number that is not finite, a block scale or zoom that is not positive, and every schema or invariant problem of a block's manifest, its path prefixed with `records`, the block's id and `manifest`.

### Ids, addresses and order

A record id is ten characters from `0-9a-z`; `mintRecordId()` draws one from the platform's cryptographic random source, rejecting bytes that would bias the alphabet. Record ids are the workspace's namespace: an address (`parseAddress`, `formatAddress`) is a record id, optionally followed by `/` and the id of an element inside that record. Timeline ids live inside a manifest: `mintTimelineId(manifest, prefix)` returns the class prefix (`clt`, `dlt`, `cpt`, `dpt`, `cgt`, `dgt`, as `TIMELINE_PREFIX` maps them) with the smallest positive suffix no timeline of the manifest uses, so ids follow timetoalign's generic scheme.

Sibling order is a fractional index: a string key that compares with ordinary string comparison, so that a record moves between two others by taking a key between theirs, without renumbering. `indexBetween(a, b)` returns one key strictly between two keys (`null` for an open end), `indicesBetween(a, b, n)` returns `n` increasing keys, and `isIndex(key)` validates one. Keys are compatible with those of Rocicorp's `fractional-indexing` 4.0.0, written in `core` ([decisions/0016](../decisions/0016-fractional-indexing.md)).

### The Yjs binding

The binding holds one manifest; a binding of the whole workspace is not part of this version. `manifestMap(manifest)` builds a `Y.Map` holding `meta`, `timeline` and, when the manifest has one, `graphical`; every timeline is a `Y.Map` of its members. `children` is a `Y.Map` by id of `{offset, timeline}` maps, `conversion_maps` a `Y.Map` by map id, `regions` and `markers` `Y.Map`s by name. Breaks and jumps are `Y.Map`s keyed by an insertion key, not `Y.Array`s: in Yjs 13.6, once the creation of an array's parent has been undone and redone, redoing the removal of one entry also removes the entry after it, because adjacent array items are merged ([decisions/0013](../decisions/0013-yjs.md) has a reproduction). Map entries are never merged. No Yjs collection carries an order; the canonical order is derived when `readManifest(map)` materializes the manifest.

Every coordinate dict, conversion-map payload, region, break and jump entry, and `meta`, `graphical`, `measure_map` and `metric_hierarchy`, is one atomic value: one string holding its `compactJson` text, read back with `parseJson`. Yjs would otherwise turn a `JsonFloat` into a plain object and wrap integers at 2^63; the text keeps every number and the order of every member.

`syncManifest(map, manifest)` writes the difference between the map's manifest and a new one, touching only the nested values that changed. The caller owns the transaction and its origin, and with it the undo manager: one transaction per command gives one undo step per command. A host runs a command through `applyToManifest` and, when it is accepted, syncs the result.

Yjs merges concurrent edits from other replicas without the reducers, so a merged manifest can break an invariant. `checkManifest` reports such a manifest and `saveManifest` refuses to write it.

## The schema contract

`@timetoalign/timeskeleton` supplies generated types, the validator, the migrations and the standard writer. The schema repository, not TiLiE, is the source of truth. The `timetoalign` library proves conformance in its own tests. TiLiE consumes that contract, preserving exact values and invoking validation at the manifest boundaries. Until timeskeleton publishes schema 0.4.0, the packages link the JavaScript package of a timeskeleton checkout beside this repository (`link:../../../../timeskeleton/js` in their `package.json`); see [CONTRIBUTING](../CONTRIBUTING.md#setup).

## Layout and writers

The drawing of a manifest is specified in the schema repository, not here: timeskeleton's [geometry specification](https://github.com/TimeToAlign/timeskeleton/blob/main/docs/geometry.md) defines the `graphical` block, the layout of a manifest as one block, and the SVG and TikZ writers completely enough that another implementation writes the same SVG and TikZ text byte for byte; a published envelope is drawn by splitting it first, one block per manifest. The specification, with the SVG and TikZ fixtures of a schema version, pins the drawing. There is no geometry schema from 0.4.0 on: the JSON form of a block is internal to TiLiE. timeskeleton keeps the geometry schema and the geometry, SVG and TikZ fixtures of 0.3.0 frozen as a record of how 0.3.0 drew an envelope; they constrain nothing.

`@timetoalign/tilie-layout` exports `layout(manifest, overrides, options)`, a pure deterministic function from a manifest to the one geometry block that draws it (a `LosslessBlock`): the root on row 0, children and conversion maps above, regions and jumps below by default, breaks through the block with their labels at the bottom end by default, wedges at the ends of every drawn line, and labels anchored as TikZ anchors nodes. Rows are filled by first fit, so a child starting where its predecessor ends shares its row. Every horizontal position is exact, on the root timeline's axis; the block carries a frame (a name column and a plot area in abstract units) and the linear map that places the root in it. Layout measures no text and knows no page.

The style cascade is a module of its own (`resolveStyle`, `scopedRules`, `rank`, `defaultStyle`, `matches`). It ranks rules first by level: a block's `overrides` (the style rules of the block record), then the manifest's own rules and timeline containers, then the default rules passed as `options.defaults`, then the written defaults. Within a level, the specification's order decides for each element and property: a rule naming the element's id, then the nearest container, then a rule naming the element type over one naming only the domain or modality, then the one naming more members, then the later rule; `visible: false` is the filter. `options.nameColumn` sets the name column's `visible` flag and its `width`, a fraction of the plot length (a hidden column has length 0 and writes no name labels). Called with no overrides and the default options, `layout` is exactly the specification's layout of the manifest: the levels above the manifest are empty and the name column is a quarter of the plot, as the specification defines it.

`@timetoalign/tilie-writers` exports `writeSvg(block, options)`, `writeTikz(block, options)` and `writeBlockSvg(block, options)`. The first two write one block on a standalone page, as the specification's section 8 writes it: the SVG page adds a margin of 16 on every side, the TikZ picture none, and the TikZ output is a complete LuaLaTeX file by default (`standalone: false` gives the `tikzpicture` alone). `writeBlockSvg` writes the same SVG elements as one `<g>` group, without a transform, with the block's top-left corner at its origin, without the page and its margin, for embedding a block in a larger drawing. Each writer computes the page transform exactly (a float in the geometry enters as its exact binary value) and formats every number by one rule, rounding to four decimal places with ties to even. Neither writer depends on the on-screen renderer. For every 0.4.0 manifest whose 0.3.0 envelope holds one top-level timeline, the output is byte for byte the SVG and TikZ fixture of that envelope; an envelope with several top-level timelines is drawn only after splitting, one block per manifest.

`app/packages/writers/scripts/emit-geometry.ts` writes the SVG and TikZ fixtures of a schema version into a timeskeleton checkout: `figure.svg` and `figure.tex` of every manifest under `fixtures/<version>/drawings/<name>/`, and no geometry JSON. Before writing anything it checks that `writeSvg(layout(manifest))` reproduces every hand-derived SVG that `fixtures/<version>/drawings/README.md` lists as `<name>/figure.svg`. It refuses a version without that README, a version whose `v<version>` tag exists, and 0.3.0; timeskeleton has no drawings for 0.4.0 yet, so today it writes nothing.

Geometry is computed per block and is intended to be memoized per block hash. PNG and JPG export, rasterized from the SVG writer's output, are intended additions; `.drawio` and PDF are reserved for a future addition.

## The server

`tilie-server` uses FastAPI and uvicorn. It binds only `127.0.0.1`, generates a random token for each run, rejects foreign Host and Origin headers, and requires `Authorization: Bearer <token>` on every `/api/` route. `tilie` hands the token to the browser in the URL fragment (`http://127.0.0.1:<port>/#token=<token>`). A browser never sends the fragment to the server, so the token does not appear in the access log; the editor reads it, removes it from the address bar and the current history entry with `history.replaceState`, and keeps it in memory only, so reloading the page after the handoff loses the token. Every response carries `Referrer-Policy: no-referrer`, so the browser sends none of the server's URLs to another site. The current server serves the built app from its wheel and implements `/api/health`; `tilie` selects a free port and opens the browser, while `tilie --check` verifies an installation.

The server is intended to load any supported source through `timetoalign` loaders; run conversion-map batches; report unfolding and traversal diagnostics with fix suggestions; validate; export; host a committed OpenAPI document and generated TypeScript client; run a CRDT room; and proxy a GitHub token. These responsibilities are not exposed by the current API.

## Packages and the dependency ladder

The TypeScript workspace is a one-way ladder enforced by [dependency-cruiser](../app/.dependency-cruiser.cjs). Lower packages never import higher packages. Only the UI packages may import Svelte.

| Package | Intended contents | Workspace dependencies |
| --- | --- | --- |
| `@timetoalign/tilie-core` | The workspace view, records, ids and order keys; the manifest value with its load, save and invariants; the commands; rationals and coordinates; the Yjs binding of a manifest; framework-free. | None |
| `@timetoalign/tilie-layout` | The layout of one manifest as one block, the style cascade and its filter. | core |
| `@timetoalign/tilie-writers` | SVG and TikZ writers over one block's geometry. | layout, core |
| `@timetoalign/tilie-arranger` | Svelte rendering of the workspace canvas and its interaction behavior; it may embed a block written by the writers. | writers, layout, core |
| `@timetoalign/tilie-client` | OpenAPI client, Arrow helpers, and CRDT provider. | core |
| `@timetoalign/tilie-editor` | The Svelte application shell and its Arranger, Inspector, and Diagnostics panes. | all workspace packages |

Packages for views and embedding are added only when a concrete need appears. Apart from `core`, `layout` and `writers`, the packages have minimal exports, and the ladder keeps `core` free of the browser.

## Testing and quality

Tests are README-first: every `tests/README.md` states the validation logic, and tests follow it. Expected values are exact. Fixtures flow from Python to TypeScript so both sides work from the same examples: `core` loads and saves every 0.4.0 manifest fixture of the schema package byte for byte and refuses every shared rejection at its pinned path. Property tests with fast-check run generated command sequences from every 0.4.0 manifest fixture and check that accepted commands keep the workspace and every block's manifest valid, that refused ones leave the view unchanged, that the Yjs binding agrees with the reducer, that undo and redo restore every intermediate manifest, and that replicas converge. `layout` reproduces, for every 0.4.0 manifest, the block that draws its timeline in the frozen 0.3.0 geometry fixture, as a regression check, and its properties hold over the same generated command sequences: the block, wrapped as a 0.3.0 geometry, still validates against the frozen 0.3.0 geometry schema, and no two elements of one row and band overlap. The writers reproduce the 0.3.0 SVG and TikZ fixture of every manifest with one top-level timeline byte for byte; the figure emitter is tested over temporary checkouts; every SVG they write parses as XML and every TikZ figure compiles under LuaLaTeX, in a CI job of its own that installs TeX Live. Current gates include Biome, Vitest, fast-check, dependency-cruiser, LuaLaTeX, Ruff, and pytest. Playwright end-to-end testing and axe-core accessibility checks are intended additions.

The editor shell test covers the token handoff through the fragment and the absent token; it does not currently cover its CSS grid layout, mobile rendering, or a fragment carrying an empty token. The server static-file tests do not currently cover traversal behavior. These limits are documented coverage gaps rather than claims of behavior.

## Performance principles

Geometry is intended to be memoized per block hash. Viewport culling and semantic zoom keep the amount of rendered detail proportional to what can be seen. Heavy data stays out of the DOM, using WebGL panes and columnar tables where appropriate. Parsing and rendering work that can block interaction belongs in workers, and server calls do not occur for every keystroke. CI budgets will make these expectations measurable.

## Automation

The command layer (`parseCommand` and `apply` over a workspace view) and the server's OpenAPI document are the intended contracts for programmatic use. An MCP server and a command channel for live sessions are reserved for a future addition. At present, the only API route is the protected health endpoint.

## Dependencies and ADRs

Each dependency requires an ADR under [`decisions/`](../decisions/). The records use MADR headings, weigh writing the component ourselves, record maintenance and exit costs, name audited versions, and include review dates. See [the ADR convention](../decisions/0001-record-architecture-decisions.md), [the TypeScript choice](../decisions/0002-typescript.md), [the Svelte and Vite choice](../decisions/0003-svelte-5-with-vite.md), [the pnpm workspace choice](../decisions/0004-pnpm-workspaces.md), [the Biome choice](../decisions/0005-biome.md), [the Vitest choice](../decisions/0006-vitest.md), [the dependency-cruiser choice](../decisions/0007-dependency-cruiser.md), [the FastAPI and uvicorn choice](../decisions/0008-fastapi-and-uvicorn.md), [the Python tooling choice](../decisions/0009-uv-hatchling-ruff.md), [the wheel bundling decision](../decisions/0010-wheel-bundles-the-built-app.md), [the exact rationals written in core](../decisions/0011-exact-rationals-written-in-core.md), [the schema package](../decisions/0012-timeskeleton-package.md), [the Yjs choice](../decisions/0013-yjs.md), [the fast-check choice](../decisions/0014-fast-check.md), [TeX Live for the TikZ checks](../decisions/0015-tex-live-for-tikz-checks.md), and [the fractional indices written in core](../decisions/0016-fractional-indexing.md).

Package manifests (`package.json`, `pyproject.toml`) declare compatible ranges for runtime and peer dependencies, such as `fastapi>=0.141,<1` in the server and the optional peer `yjs` `^13.6.33` in `core`; development dependencies, the npm `devDependencies` and the server's `dev` group, are pinned exactly. Lockfiles pin every resolved version: `server/uv.lock` for Python and `app/pnpm-lock.yaml` for the application. A version must have been released at least 14 days before it enters a lockfile, and the ADR identifies the audited version. The one exception to that window is this project's own schema package, `@timetoalign/timeskeleton` (`minimumReleaseAgeExclude` in `app/pnpm-workspace.yaml`), so that a schema release can be consumed as soon as it is published. This policy deliberately separates compatibility declarations from reproducible resolutions.

## Deployment

Install the current product with `pip install tilie-server`, then run `tilie`. The installed wheel contains the built browser app, so starting it does not require Node.js or a runtime download.

The deployment model is intended to grow toward a hosted browser app that communicates with a user-run local server, a desktop wrapper, and collaborative hosting. Those deployment forms are not available today.
